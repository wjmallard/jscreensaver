# halftone — port notes

Port of `halftone.c` by Peter Jaric (2002) — a regular grid of dots whose sizes are driven by the summed gravitational field of several moving point-masses, so the grid ripples and pulses like a halftone print of a slowly churning gravity well. "View it from a distance for best effect."

Original: <https://www.jwz.org/xscreensaver/> · source: `xscreensaver-6.15/hacks/halftone.c` (412 lines). Follows the [[squiral]] skeleton; closest technique twins are [[grav]] (moving point-masses) and [[spiral]] (sparse per-frame draw over a clear).

## Algorithm
- **Masses**: `count` point-masses, each with a position in the normalized 0..1 box, a `mass` in `[minMass, maxMass]`, and a per-axis speed in `[minSpeed, maxSpeed]`. Each step a mass at or past an edge (`pos >= 1 || pos <= 0`) negates that axis's increment, *then* the increment is added — so they bounce inside the box.
- **Field**: the dot grid is `dotsW = floor(width/spacing)+1` by `dotsH = floor(height/spacing)+1`. For each grid node `(x,y)`, `calculateGravity` sums each mass's field as a *vector*: a mass at fraction `(gx,gy)` sits at grid coords `(gx*dotsW, gy*dotsH)`; with `dist` the grid-space distance, each contributes `mass * dotsW * dotsH / dist^2` along the unit direction to the mass. The node's value is the **length of the summed vector** (not the sum of magnitudes — vectors can cancel), clamped to `[0,1]`.
- **Paint**: fill the background in `colors[color0]`, latch the dot colour `colors[color1]`, advance both cycling palette indices every `cycleSpeed+1` ticks, then draw every node as a filled disc of diameter `trunc(maxDotSize * field)` (`fill_circle` takes an `int` size, and `max_dot_size = sizeFactor * spacing` is itself an `int`, so dot sizes are integer-quantized). Per frame the C does `repaint` then `update` (move masses + recompute field). Note the C latches the dot foreground into the GC *before* the cycle tick, so on an advance frame the dots still use the old colour — both colours take effect together the next frame; the port preserves this ordering.
- **Colours**: one 200-entry `make_smooth_colormap` (`*colors: 200`), built once in `halftone_init` and never rebuilt. `color0 = 0` is the background, `color1 = ncolors/2` the dots — complementary positions on the same smooth map, creeping forward one entry every `cycleSpeed+1` frames (`*cycleSpeed: 10`), so the pair drifts slowly around the map together. Ported via `colormap.js` `makeSmoothColormapRGB(200)`.

## Shared skeleton
Standard for the gallery (see [[squiral]]): a no-build ES module exporting `title` / `info` / `start(canvas) → { stop, pause, resume, reinit, config, params }`; an rAF **lag-accumulator** loop paced at `(config.delay + OVERHEAD)` µs (catch-up capped so a backgrounded tab can't burst); `devicePixelRatio` folded into sizes; the host renders the config box from `config`/`params`.

## Deviations from the C
- **No off-screen Pixmap.** The C double-buffers into a `buffer` Pixmap then `XCopyArea`s to the window. The browser already composites the canvas, so we clear + draw straight to it; no flicker. (`update_buffer` and the whole buffer/buffer_gc bookkeeping are dropped.)
- **Retina via `devicePixelRatio`, not a 2560 px threshold.** The C triples `spacing` once the window exceeds 2560 px. We instead scale `spacing` by `devicePixelRatio` (`S`) so dots stay a consistent CSS size and crisp on retina; `maxDotSize = trunc(sizeFactor * spacing)` follows (so the integer dot-size quantization lands on device px, exactly as the C's does on its own pixels). `spacing` is floored at 2 px so a dot is always visible.
- **First frame is already filled.** The C's `halftone_draw` paints *before* the first `update`, so its frame 1 shows all-zero (invisible) dots. We call `updateField()` at the end of `initGeometry()`, so the very first painted frame already shows the halftone pattern (per the brief's "first frame looks right" mandate).
- **Resize re-grids in one shot.** The C's `halftone_reshape` is empty; instead `update_halftone` re-reads the window attributes *every tick* and re-derives the buffer + dot grid, keeping the palette, colour-cycle position, and masses. The port does the same work once, from the resize event (`initGeometry()`): the grid and field are rebuilt, everything else carries over. Only `reinit()` (a config change = a fresh run of the binary with new flags) re-rolls the palette and re-seeds the masses.
- No XOR / feedback raster tricks are involved, so none needed emulation.

## Config
Units/labels mirror `hacks/config/halftone.xml` — exactly its eight sliders: `delay` (stock **10000**, `invert: true` per the xml's `convert="invert"` "Frame rate" slider), `count` 1–50, `spacing` ("Dot size") 2–50, `sizeFactor` ("Dot fill factor") 0.1–3, and the four speed/mass ranges 0.001–0.09. `live: true` on `delay` only; the rest size the grid / masses, so a change re-runs `init()` via `reinit()`. The C's `*colors: 200` and `*cycleSpeed: 10` resources have **no xml knob**, so they are behaviour constants (`NCOLORS` / `CYCLE_SPEED`), like mountain's `cycles`. The loop paces at `(delay + OVERHEAD)` µs; `OVERHEAD = 9950` is the live-measured per-tick draw cost of the binary (full-window fill + one `XFillArc` per grid node + buffer copy): `-fps` showed 50.1 fps at Load 49.9% — a clean reading, the sleep slice `19960·(1−0.499) = 10000` equals the stock delay exactly.

## Correctness self-review
- **No termination / closure state to stall.** This hack has no figure-closing or grid-fill-then-clear state machine (unlike squiral) — every frame it unconditionally clears, moves the masses, and recomputes the whole field. There is no branch that could leave the next frame reading un-reseeded state, so the "dead lines / endless over-draw" failure modes don't apply. The masses move from frame 1 (`moveMasses` runs in every `step`, and the field is already seeded in `initGeometry`).
- **Divide-by-zero guarded.** `calculateGravity` only accumulates when `dist !== 0`, exactly as the C does, so a mass landing exactly on a grid node is skipped rather than producing `Infinity`. Positions are doubles seeded by `Math.random()` and advanced by irrational-ish increments, so exact coincidence with an integer node is effectively impossible anyway; the guard is belt-and-suspenders, matching the C.
- **Radius bounded — no blow-up.** The node value is clamped to `[0,1]` before paint, so the disc diameter is bounded by `maxDotSize = sizeFactor * spacing`. At the default `sizeFactor` 1.5 the max diameter is `1.5*spacing > spacing`, so in dark regions dots touch/overlap — this is the intended halftone look and is faithful to the C (which likewise allows `sizeFactor` up to 3). The clamp is what prevents an unbounded "overlap blowout": however close a mass gets to a node, that node's value saturates at 1.
- **Bounce ordering preserved.** The edge test runs against the *current* position before the move (matching the C). Because the speed range is small (≤0.09/step) relative to the box, a mass overshoots an edge by at most one step's increment and is turned back the next frame — it can't escape and stop contributing. `pos <= 0`/`pos >= 1` (not strict) ensures a mass parked exactly on a boundary still flips.
- **pause/resume / reinit.** `pause` cancels the rAF and sets `rafId = 0`; `resume` resets `lastTime = 0` before re-arming, so no catch-up burst and the masses pick up exactly where they paused (no jump). `reinit` re-seeds everything and clears to black for a clean fresh screen.
