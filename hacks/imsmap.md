# imsmap — port notes

Port of `imsmap.c` by Juergen Nickelsen & Jamie Zawinski (1992; derived from code by Markus Schirmer, TU Berlin) — recursive cloud-like fractal patterns (a plasma / diamond-square height-field) displayed through a smoothly cycling colour map. Follows the shared skeleton in [[squiral]]; renders via the Uint32 ImageData blit idiom of [[thornbird]] / [[binaryring]].

Original: <https://www.jwz.org/xscreensaver/> · source: `xscreensaver-6.15/hacks/imsmap.c` (~426 lines)

## Algorithm
A height-field is grown by **midpoint subdivision** (the plasma fractal). The four screen corners start at height 0. Then, repeatedly, every cell is split: each new edge-midpoint is set to the average of its two flanking corners, and each new centre-midpoint to the average of all four corners — plus a random offset whose amplitude **halves at every level** (`rang = 1 << (NSTEPS - level)`, NSTEPS = 7, so the coarsest level perturbs by ±64 and each finer level by half that). Heights are mapped to a valid palette index by `HEIGHT_TO_PIXEL`: normally saturating (below 0 → 0, at/above ncolors → ncolors-1), but on a random 1-in-5 of regenerations (`extra_krinkly_p`) out-of-range heights instead **wrap** through the colormap, banding the cloud. The result is a smooth fractal cloud of integer heights, which is shown by looking each cell's height up in an `ncolors`-entry colour map.

In the original C, the subdivision **is** the visible drawing (cells are painted as they're set, `iteration*2+1` columns per frame, coarse levels as big filled rectangles and fine levels as small ones), and once the map is finished it lingers `delay` seconds, then `init_map()` grows a fresh one.

## This port
- **Generate once, cycle the palette for motion.** The whole field is grown in one `generateField()` call into a `Uint16Array` (one cell per canvas pixel), then each frame advances a float `cycleOffset` and blits `palette[(height + offset) mod ncolors]` for every pixel via one `putImageData`. The colour map is the faithful **`make_smooth_colormap`** (`colormap.js`) — a random 2-5 anchor HSV loop, frequently muted/pastel — and is a closed loop (wraps end-to-end), so rotating it through the static cloud is a seamless plasma shimmer. A fresh field **and a fresh colour map** are generated every `delay` seconds — matching the C, where `init_map` rebuilds the colormap on every regeneration.
- **Subdivision kept faithful.** Same corner-seed, same edge/centre midpoint averages, same per-level halving random amplitude (`1 << (NSTEPS - level)`), same `HEIGHT_TO_PIXEL` mapping (saturate, or wrap on the 1-in-5 `extra_krinkly_p` regenerations). Each set midpoint is painted as a `nextStep`-sized block (`fillBlock`), exactly as the C's `draw()` tiles the screen with `XFillRectangle` of size `ynextStep`, so coarse levels lay down big blocks and finer levels overwrite with detail — the field ends up gap-free. `iterations` (Density) is the number of subdivision levels, 1..7, clamped like the C.
- **devicePixelRatio**: backing store sized in device px (`resize()`), field sized from `canvas.width/height`, so the cloud is full-resolution and crisp on retina.
- **Standard shared skeleton**: rAF **lag-accumulator** loop paced by `config.delay2` µs (the per-frame budget, the xml's "Frame rate"); `pause`/`resume` (reset `lastTime`, `rafId === 0` sentinel); `stop` removes the resize listener; `reinit` rebuilds palette + field.

## Deviations from the C
- **Motion source changed (deliberate, per the porter brief).** The C animates by *drawing the subdivision incrementally* and re-rolling the whole map after a linger; we animate by *cycling a cyclic smooth palette* over a pre-generated field and regenerate on the same linger interval. The visible result — a slowly shifting fractal cloud that periodically reshapes — is in the same spirit; the build-up "wipe-in" of the C's progressive draw is not reproduced (the new field simply replaces the old one).
- **Edges clamp instead of wrap.** The C wraps the right/bottom neighbour index to the opposite edge (`x2 >= xmax -> 0`), which on its toroidal field keeps midpoints defined; on a non-toroidal canvas that would fold the far edge into the near one, so we clamp the neighbour to the last row/column. Cosmetic — only the outermost seam differs, and it stays smooth.
- **`flip_x` / `flip_xy` dropped.** The C randomly swaps x/y and/or mirrors x purely to reorient the same cloud; with a generate-then-blit field this is a no-op on appearance, so it's omitted.
- **Mono / Floyd–Steinberg path dropped.** The C has a 1-bpp dithered fallback (`floyd_steinberg`) for `mono_p`/`ncolors <= 2`; we always run colour (min 3 colours via the xml range), so the dither path isn't ported.
- **`mode` is vestigial — faithfully so.** `imsmap.c` declares the `mode` resource (random / h / s / v, also in the xml) but **never reads it**; the colormap is always `make_smooth_colormap`. The port keeps the `mode` control for xml / config-box parity, but, like the C, it no longer selects a palette flavour (changing it just re-rolls a fresh random cloud via `reinit`).
- **Palette is the faithful `make_smooth_colormap`** (`colormap.js`): a random 2-5 anchor HSV loop, frequently muted/pastel, re-randomized on every regeneration — not a fixed vivid rainbow. Default `delay2` (frame budget) and `delay` (linger) match the xml (20000 µs, 5 s).
- **Framerate calibration (`OVERHEAD = 12680`, build phase only).** `delay2` (the per-chunk paint interval) is a sleep floor; the live binary's real build rate is lower (delay2 + framework overhead — see the framerate-calibration note). The live imsmap measures **30.6 fps** during the coarse→fine build, while the port at the stock `delay2 = 20000 µs` ran 50 chunks/sec (1.63× fast). The loop adds `OVERHEAD` to the per-chunk delay only — `20000 + 12680 = 32680 µs → 30.6 chunks/sec` — and the `delay`-second finished-cloud **hold is left untouched**. The `delay2` slider still maps 1:1 to the xml resource.
- **Added `cycleSpeed`** (palette steps per frame) — not in the C; it controls the shimmer rate, which here is the motion. `cycleSpeed = 0` freezes a still cloud.
- **ASCII-safe encoding**: the only rendering string with a non-ASCII glyph is the frame-rate unit, written `' µs'` (micro sign). All other non-ASCII bytes are em dashes in comments only.

## Correctness self-review
- **No uninitialized / out-of-range cells.** The height buffer starts all-0 (a valid palette index); subdivision only ever writes `HEIGHT_TO_PIXEL`-clamped values. A headless re-implementation over several sizes/params confirmed `min >= 0 && max < ncolors` in every case, so the per-pixel palette read can't go out of bounds (no `undefined`/NaN pixels). At iterations = 7 the field uses the full palette (50 of 50 distinct values) with only ~7 % of cells left at height 0 (genuine low cells + the sub-pixel top-left corner, all valid palette[0]); at iterations = 1 it's intentionally coarse (~43 % palette[0]), matching the C's "Sparse".
- **No freeze / no endless over-draw.** There is no figure-closure or float-equality reset to get stuck on; the loop is a bounded per-pixel map plus a periodic regenerate. The subdivision loop is finite: `xstep`/`ystep` strictly halve and the loop breaks once both `nextStep`s drop below 1, so `generateField()` always terminates. The regenerate trigger counts real per-frame budgets (`delay2` µs → ms), so the linger is honest regardless of cycle speed; it's independent of the catch-up cap, so a long background pause can't wedge it.
- **Palette cycle wraps cleanly.** `off = ((floor(cycleOffset) % ncolors) + ncolors) % ncolors` is always in `[0, ncolors)` for negative or large offsets (verified), and the rotated palette is recomputed once per frame, so the inner pixel loop is a single array read.
- **pause/resume / reinit.** `pause` cancels rAF and parks `rafId = 0`; `resume` resets `lastTime` so no catch-up burst. `reinit` re-runs `init()` (fresh ImageData cleared to black, fresh palette, fresh field, immediate first render) — a clean new screen. The first frame already shows the full cloud (`init()` calls `generateField()` then `render()` before the loop starts), so there's no blank/degenerate start.
- **One risk to spot-check in the browser**: the per-frame cost is `W*H` palette lookups + a `putImageData` (e.g. ~2.07 M pixels at 1080p). That's the same per-frame work as thornbird/binaryring's blit and runs well, but on a very high-DPI 4K display it's worth a glance that the default `delay2` keeps it smooth. The visual to confirm is a smooth, slowly-shifting cloud (not a flat wash and not flickering), regrowing every ~5 s.
