# strange — port notes

Port of `strange.c` by Massimino Pascal (1997); accumulator mode, varying colours, point size / zoom / brightness / motion blur added by dmo2118 (2017). A 2-D **strange attractor**: a swarm of dots swoops and twists around as the map's random coefficients drift, with denser regions of the orbit glowing brighter.

Original: <https://www.jwz.org/xscreensaver/> · source: `xscreensaver-6.15/hacks/strange.c` (~1352 lines). See [[thornbird]] and [[hopalong]] for the strange-attractor point-plot twins, and [[squiral]] for the shared module skeleton.

## Algorithm
Each frame iterates one of two non-linear polynomial maps in fixed-point (`UNIT_BITS = 12`, so world `[-1, 1]` lives in `[-UNIT, UNIT] = [-4096, 4096]`):

- **Iterate_X2** — `xo = fold(P0 - y + poly1(x,y));  yo = fold(P5 + x + poly2(x,y))`, where `poly1/2` are weighted sums of `x², xy, y², x²y/ y²x` and `fold()` is an odd-extended sine lookup (`Fold[i] = sin(i/UNIT)`). This is the classic "swarm of dots".
- **Iterate_X3** — same numerators plus a third polynomial `z`, then a projective divide `xo = tx·UNIT / (UNIT + z²)`. Wilder; can collapse to a tiny cluster for some coefficients.

The 15 coefficients come from `Old_Gauss_Rand(mid, amp, 4)` — `c ± A·(z − e^(−y²S))/(z − e^(−S))` with `z = curve/10`, `y` uniform. Each frame the **current** coefficients interpolate from `prm1` toward `prm2` (`u = count/40000`); when `count` reaches 1000 it commits (`prm1 = prm2`) and rolls a fresh `prm2`, so the figure morphs through an endless sequence of attractors. `curve < 10` forces the projective X3 map (the C avoids "boring" X2 there); otherwise the map is picked 50/50 at init.

Rendering is the **accumulator** path: from the origin, settle `SKIP_FIRST = 100` iterations (with a small ±4 jitter, as the C does), then plot `points` iterations, each `accMap[y*W+x]++` (an intensity / hit-count field). Optional **motion blur** is an IIR feedback over that field (`buf = buf·blurFac + intensity`, `blurFac = (mb−1)/(mb+1)`), leaving trails as the attractor moves. Finally the field is colour-mapped through a logarithmic ramp built around a slowly-cycling base hue.

## Rendering approach
Dense per-pixel **ACCUMULATOR / BLIT** path (like [[thornbird]] / [[binaryring]]): a `Uint32` intensity field (`accMap`) we `++` per point hit, a `Float32` working/feedback field (`motionBuf`), and a second `Uint32` `ImageData` buffer we colour-map and `putImageData` once per frame. Note that — unlike thornbird/hopalong, which accumulate progressively onto a persistent canvas — strange **rebuilds the intensity field every frame** (the C `memset`s `accMap` each frame); the animation is the coefficient drift plus the IIR motion-blur feedback, not a growing canvas.

## Deviations from the C
- **Intensity → colour mapping (the significant one).** The C uses a fixed `colorScale` calibrated (with `<<COLOR_BITS` fixed-point) so that dense spots saturate at the top of a 150-entry ramp. Numerically reproduced on the web that constant is ~95 at default settings, so even a **single** hit lands near the top of the ramp — the whole figure flattens to a near-uniform bright curve with no visible density gradient. Instead this port **normalises per frame on a log curve**: `cIdx = lastCol · log(1 + k·v) / log(1 + k·maxV)`, where `maxV` is the frame's peak intensity and `k = brightness·colorFac·8`. This uses the full ramp end-to-end every frame and always shows the bright-core → dim-edge glow, for both the sparse X2 swarm and dense X3 attractors. `brightness` scales the log knee; `colorFac = 2/(mb+1)` still compensates for the motion-blur energy gain. (Verified by simulation: the swarm spans ramp indices ~52–98; spread-out X3 attractors span ~24–99.)
- **Colour cycling / palette.** The C ramps a single queried base colour from near-black to bright and only re-hues in TrueColor. This port builds a **vivid HSL rainbow base hue** that drifts with the frame counter (`col`), per the project's "vivid over muted" aesthetic, then runs it through the C's exact `ramp_color` log curve (`ACC_GAMMA = 10`, `MINBLUE/FULLBLUE`).
- **Box-blur bloom.** The C does an incremental, separable box blur of radius `pointSize` (a clever O(1)-per-pixel running sum). This port does a **direct `pointSize × pointSize` block sum** per pixel — simple and exact for the default `pointSize = 1` (a single read), but O(pointSize²) per pixel, so large point sizes on retina are slow (see caveat). The bloom expands rightward/downward to match the C's in-place expansion direction.
- **Retina point size.** The C triples `pointSize` past 2560 px; this port scales it by `devicePixelRatio` instead, so a logical size of 1 stays a crisp ~1 CSS px.
- **No threads / no XShm.** The C splits the field across worker threads and blits via shared memory; here it's a single JS loop with `putImageData`. Pure performance plumbing, no visual effect.
- **Fixed-point in doubles.** PRM is a 32-bit `int` in the C; JS numbers are doubles, so the polynomial products (which can exceed 2³¹) stay exact, and `>>UNIT_BITS` is done as `Math.floor(v/UNIT)`. The `& (UNIT2−1)` fold index is applied to a value first coerced with `|0` (always in range there), matching the C's wraparound.
- **`ncolors` exposed.** The xml's `ncolors` (ramp size, default 100) maps to `numCols`; the C hardcodes `DEF_NUM_COLS = 150` in colour mode.

## Correctness self-review
- **First frame is never blank.** Simulated 12 fresh attractors (X2 and X3): **all 5500 points landed in-bounds**, zero NaN/inf, every frame lit ≥ 3 pixels. The world box is fixed to `[-UNIT, UNIT]` and `Lx/Ly` map it to fill the canvas, centred — so the scale always covers the screen (no off-screen/degenerate start). `fold()` (sine) bounds the X2 output to `[-UNIT, UNIT]`; the X3 projective divide bounds its output; the per-iteration `±4` jitter keeps the orbit from sticking — so coordinates can't run to infinity, and there is no divergence to guard with a reseed.
- **`Tmp_z0 == 0` guard** kept verbatim (the C's `-curve 9` corner) — `if (tz0 === 0) tz0 = 1` avoids a divide-by-zero in X3.
- **Degenerate X3 clusters don't linger.** When an X3 attractor collapses to a handful of pixels it renders (the log-normalise still shows it), and the C's **`VARY_SPEED_TO_AVOID_BOREDOM`** acceleration is reproduced: while the lit-pixel count is tiny the drift `speed` ramps 4 → 32, so `count` reaches 1000 sooner and the attractor rolls over to a fresh one. So a boring attractor is transient, not a permanent dead dot.
- **Drift never freezes.** `count` increments every frame by `speed ≥ 4`; at `count ≥ 1000` it commits and rerolls. There is no float-equality / closure test that could fail to fire (the past-port failure mode) — it's a plain integer accumulator. The morph reaches a new attractor at least every `1000/32 ≈ 32` to `1000/4 = 250` frames.
- **Motion-blur IIR converges.** Simulated 30 frames: `maxV` stabilises (≈ 2× single-frame for the default `mb = 3`, matching the geometric-series steady state `1/(1−blurFac)`) — no runaway to white, no decay to black; `lit` grows as the trail fills, giving the dense morphing cloud. The per-frame `maxV` normalise keeps exposure correct throughout.
- **pause → resume** resets `lastTime = 0` (no catch-up burst). **reinit** (non-live config change) re-runs `init()`: fresh buffers, fresh coefficients, black canvas. `live` params (`delay`, `zoom`, `brightness`, `motionBlur`) are read each frame and apply instantly; `curve`, `points`, `pointSize`, `ncolors` size buffers / pick the map, so they reinit.

## Caveats / spot-check in browser
- **Default look is a sparse, faint swarm.** The xml default `points = 5500` lights only a few thousand pixels per frame (faithful — the C's own hint suggests `-points 500000` for the dense look). The **motion-blur default (3.0)** builds that swarm up over frames into a brighter morphing cloud, which is the intended default. Worth a look that it reads as "a swarm that swoops and twists", not a dim speckle — bump **Number of points** and/or **Brightness** if it's too faint on a given display.
- **Performance:** two full `W×H` passes per frame; on a high-DPI display that's millions of pixels twice per frame. The lag-accumulator caps catch-up at `MAX_CATCHUP_STEPS = 4`, so it degrades to a lower frame rate rather than stalling. **Large `pointSize` on retina is the slow case** (O(pointSize²) per pixel block sum) — fine at the default 1.
- **First-frame X3 collapse:** roughly half of fresh attractors use X3, and a fraction of those start collapsed to a tiny cluster for a moment before the boredom-acceleration drifts them out. Expected and transient, but a reviewer hitting `r` (reinit) repeatedly will occasionally catch one mid-collapse.
