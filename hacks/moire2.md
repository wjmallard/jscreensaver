# moire2 — port notes

Port of `moire2.c` by Jamie Zawinski (1998) — fields of concentric circles (zone plates) drifting past one another, their additive/XOR interference spraying moire fringes through a cycling colour map. This is the **multi-zone-plate** moire (distinct from `moire`, the single warped grating).

Original: <https://www.jwz.org/xscreensaver/> · source: `xscreensaver-6.15/hacks/moire2.c` (~362 lines)

## Algorithm
Two or three ring-fields (the C's `do_three` = `random()%3==0` gives 3, else 2), each a set of concentric circles centred at a point that drifts independently. The C draws each field into a 2x-size 1-bit pixmap (concentric `XDrawArc`s stepping by ~thickness px), then every frame copies a window-sized slice from a drifting offset onto an accumulator with **OR** or **XOR**, and paints the 1-bit result in a single colour that cycles through a smooth colormap (`pix = (pix+1) % ncolors`). Centres bounce around via a `FROB` macro (advance by a velocity, reflect at the edges, occasionally reverse or nudge the velocity). Every `colorShift` frames an iteration counter ticks down; after `30 + random%70 + random%70` ticks the whole scene re-rolls (new field count, ring spacing, centres, velocities, combine mode).

This port computes the same field **directly per pixel** instead of via scrolling pixmaps: for each pixel and each field, the ring index is `floor(distance_from_centre * freq)` (freq = 1/spacing); the indices are combined across fields by **summing** (additive moire — the default look) or **XOR** (parity), then `(total + phase) mod ncolors` indexes the palette, where `phase` advances one step per frame (the colormap cycle). Centres drift with a faithful port of the C's `FROB` velocity model. Re-roll cadence (`colorShift`, the `30+...` iteration count) matches the C.

## Module shape
`start(canvas) -> { stop, pause, resume, reinit, config, params }` — see [[squiral]].

## Rendering — blit at logical resolution
A dense per-pixel field rebuilt every frame, so it uses the **BLIT path** like [[metaballs]] and [[binaryring]]: a `Uint32` `ImageData` filled by indexing the palette per pixel, one `putImageData` into an offscreen scratch canvas, then `drawImage`-upscaled onto the device-px main canvas. The field is computed at **logical (CSS-pixel) resolution** (`canvas.width / devicePixelRatio`) and the canvas scales it up — one sqrt per source per logical pixel, so the cost is independent of dpr. The C does the morally equivalent thing with its `".lowrez: true"` default ("Too slow on Retina screens otherwise"). At 2 sources this is comfortably real-time; 3 sources is heavier but holds up at the default delay.

**Default delay:** 40000 µs (the C's 50000, nudged a touch faster — the calm shimmer reads better slightly quicker; still well below stock pace per frame of pixel work).

## Deviations from the C
- **Per-pixel field instead of scrolling 1-bit pixmaps.** The X11 version pre-renders rings into `width*2 x height*2` bitmaps and scrolls a window over them (cheap blits, no per-pixel math). Canvas has no equivalent `XCopyArea`-with-raster-op, so the ring field is evaluated directly: `floor(dist*freq)` is a concentric-ring index, which is exactly what the pre-rendered arcs encode. Same picture, different machinery.
- **OR -> additive sum.** The C's OR-combine of 1-bit planes is replaced by **summing ring indices** before the palette lookup — the additive interference the description ("combines the planes... interference lines spray") is really about. This is richer than a 1-bit OR (it yields the full moire beat pattern rather than a 2-colour union) and is what the "sum each zone-plate's contribution, map through the palette" brief asked for. **XOR** is kept faithfully as an alternate combine (parity of ring indices), chosen on the same conditions as the C (`do_three`, `thickness==1`, or a coin flip); at logical resolution the upscale smooths its higher-frequency result.
- **Single cycling colour -> full palette indexed by the field.** The C paints the 1-bit mask in one colour that cycles; here every pixel's summed field value indexes the cycling palette directly, so the rings themselves are rainbow-banded (vivid full-spectrum `hsl` ramp, per project taste) rather than monochrome-on-black. The *cycling* is the same `pix`/`phase` increment per frame.
- **No GXxor self-fill / random maxx,maxy stretch as literal ops.** The C's occasional `GXxor` rectangle fill over a plane and `maxx/maxy *= 1+frand(0.05)` oval-stretch are folded into the model as a small per-field random spacing detune (`freq` jitter), which keeps the fields from phase-locking — the same visual purpose (asymmetric, beating fringes) without the pixmap tricks.
- **Encoding:** the micro sign in the "Frame rate" unit is the `µs` escape (no literal non-ASCII in any rendered string); literal Unicode appears only in comments.
- **Config:** added `colorShift` (a real C resource, absent from the stock xml UI) as a "Cycle speed" slider, and `sources` (surfacing the C's hidden 2-or-3 choice) so the field count is tunable; `0 = auto` reproduces the C's `random()%3` each re-roll. `thickness` maps to ring spacing. Keypress fg/bg flips (`flip_a`/`flip_b`) are dropped — they only swapped which colour cycled in the 1-bit scheme, which has no analogue here.

## Correctness self-review
- **First frame is non-degenerate.** `init()` runs `resetScene()` before frame 0, seeding 2–3 sources with nonzero `freq`, so the opening frame already shows concentric rings. Centres start at `MAX/2 + random%MAX` (often partly off-screen, faithful to the C's copy offset); since the ring index grows with distance and `freq > 0`, the viewport still shows varying arcs even when a centre is off-screen.
- **It cannot go static.** `phase` advances every single frame and indexes the palette modulo `ncolors`, so the bands shimmer continuously even on a frame where every centre's velocity momentarily stalls. (A velocity *can* reach 0 via the C's nudge, exactly as in the original; it recovers on a later nudge, and the colour cycle never stops, so there is no freeze.)
- **Re-roll re-seeds everything the next step reads.** `resetScene()` reassigns `nsources`, `xorMode`, and a fresh `sources` array with all of `x, y, dx, dy, freq`; `iterations` is reset to `30 + random%70 + random%70` *before* the next countdown. No stale field is carried across a reset, so no half-initialised source is ever drawn.
- **No exact-float closure / over-draw risk.** There is no figure-closure test (the failure mode that killed earlier ports). The only termination is the integer iteration countdown (`iterations--` guarded by `<= 0`), which always fires.
- **Loop bounds.** The rAF lag-accumulator is the shared pattern with `MAX_CATCHUP_STEPS` and `lag` capping, and `config.colorShift` is read through `Math.max(1, ...)` so a 0/negative value can't stall the countdown. `pause()` (`rafId = 0` sentinel) then `resume()` (`lastTime = 0`) does not burst; `reinit()` rebuilds buffers/palette/sources and clears to black.

## Config
`delay` (Frame rate, live, invert) · `colorShift` (Cycle speed, live, invert) · `thickness` (Ring spacing; 0 = auto, reinit) · `sources` (Ring-fields; 0 = auto, reinit) · `ncolors` (reinit). Defaults mirror `hacks/config/moire2.xml` (delay 50000 -> 40000, ncolors 150, thickness 0) plus the two added keys (colorShift 5, sources 0).
